# 서버 설계 결정

결정마다 이유와 버린 대안을 짧게 남깁니다.

## 스레드 모델: 단일 스레드 루프

- **결정:** 스레드 하나가 입출력 대기(`poll`)와 틱을 번갈아 처리합니다.
- **이유:** 잠금이 없어 코드를 따라 읽기 쉽고, 메시지 처리와 틱 사이의 경쟁 상태가 생기지 않습니다. P1의 100명 규모에 충분합니다.
- **대안:** 네트워크 스레드와 게임 스레드 분리. 입출력이 틱을 막지 않지만 스레드 간 큐가 필요합니다. 측정에서 필요성이 확인되면 그때 나눕니다.

## 소켓 입출력: 논블로킹 + WSAPoll

- **결정:** 모든 소켓을 논블로킹으로 두고 `WSAPoll`로 준비된 소켓만 처리합니다.
- **이유:** 준비 여부를 묻고 처리하는 흐름이 코드에 그대로 보입니다.
- **대안:** IOCP. Windows에서 대규모 접속에 가장 적합하지만 비동기 완료 모델이라 구조가 복잡합니다. 접속 수가 늘어 `WSAPoll`의 전체 순회가 문제가 되면 `ITransport` 뒤에서 교체합니다.

## 전송 계층 분리: ITransport

- **결정:** 게임 로직은 `ITransport`로 완성된 프레임만 주고받습니다. TCP 길이 프리픽스는 `TcpTransport` 안에만 있습니다.
- **이유:** 브라우저 배포로 결정되면 WebSocket 구현을 추가하기만 하면 됩니다. WebSocket은 메시지 경계가 이미 있어 길이 프리픽스가 필요 없습니다.
- **대안:** 게임 코드가 소켓을 직접 사용. 더 짧지만 전송 방식을 바꿀 때 게임 코드를 고쳐야 합니다.

## 존과 네트워크 분리: IZoneObserver

- **결정:** `Zone`은 네트워크와 Protobuf를 모르고, 일어난 일을 `IZoneObserver`로 알립니다. `GameServer`가 이를 메시지로 바꿉니다.
- **이유:** 세계 규칙과 통신 형식을 따로 읽고 고칠 수 있습니다.
- **대안:** `Zone`이 직접 메시지를 전송. 호출이 줄지만 규칙과 직렬화가 섞입니다.

## 인위 지연: LagTransport 데코레이터

- **결정:** `--lag-rtt-ms`를 주면 `LagTransport`가 `TcpTransport`를 감싸 수신과 송신을 절반씩 늦춥니다.
- **이유:** 디버그 기능이 게임 로직과 실제 전송 코드에 섞이지 않습니다.
- **대안:** Clumsy 같은 외부 도구. 코드는 필요 없지만 재현 조건을 저장소에 남기기 어렵습니다.

## 틱: 고정 간격과 따라잡기 상한

- **결정:** 다음 틱 시각에 100ms씩 더해 평균 10Hz를 유지합니다. 5틱 이상 밀리면 놓친 틱을 버립니다.
- **이유:** 처리 시간이 누적되어 틱이 느려지는 것을 막고, 오래 멈춘 뒤 틱을 몰아 돌리는 일도 막습니다.
- **대안:** 매 틱 뒤 100ms 대기. 단순하지만 처리 시간만큼 주기가 늘어납니다.

## 타이머 해상도 1ms

- **결정:** 서버 실행 중 `timeBeginPeriod(1)`을 켭니다.
- **이유:** Windows 기본 대기 단위는 약 15.6ms라 틱과 인위 지연의 정확도가 떨어집니다.
- **대안:** 기본값 유지. 전력 소모는 적지만 지연 측정 오차가 커집니다.

## AOI: 틱마다 전체 쌍 거리 계산

- **결정:** P1은 플레이어 쌍마다 거리를 계산하고, 진입 700과 이탈 800으로 나눕니다.
- **이유:** 100명 이하에서는 단순 계산으로 충분합니다. 격자 같은 최적화는 P5의 학습 주제입니다.
- **대안:** 격자 분할. 지금은 성능 이득보다 코드 부담이 큽니다.

## 메시지 스키마: common과 packet 분리

- **결정:** 공용 타입은 `common.proto`, 클라이언트↔서버 메시지는 `packet.proto`에 둡니다. 메시지 번호는 구간별로 나눕니다(입장 1000번대, 월드 2000번대).
- **이유:** 서버 내부 메시지를 추가할 때 공용 타입을 함께 쓸 수 있고, 번호만 봐도 구간을 알 수 있습니다.
- **대안:** 파일 하나 유지. 지금은 더 단순하지만 메시지가 늘면 구간을 구분하기 어렵습니다.

## Protobuf를 C++20으로 빌드

- **결정:** `triplets/` 오버레이로 vcpkg의 Protobuf와 abseil을 서버와 같은 C++20으로 빌드합니다.
- **이유:** Protobuf 헤더는 C++ 표준에 따라 타입이 달라집니다. 포트 기본값인 C++17로 쓰면 Release 링크가 실패합니다.
- **대안:** 서버를 C++17로 낮추기. 설정은 줄지만 `std::span` 같은 기능을 잃습니다.
- **주의:** triplet을 바꿔도 `vcpkg.json`이 그대로면 MSBuild가 설치를 건너뜁니다. 기존 `vcpkg_installed`는 지우고 다시 빌드합니다.

## Debug 구성: 릴리스 런타임 + ASan

- **결정:** Debug도 릴리스 CRT, 릴리스 라이브러리, `NDEBUG`를 쓰고 최적화만 끕니다. ASan은 켜 둡니다.
- **이유:** Protobuf 생성 코드의 해시비트 검사는 `NDEBUG`가 없으면 켜지는데, 이 환경에서 잘못된 주소를 읽어 서버가 죽습니다. ASan을 감지해도 같은 검사가 켜지므로, 강제 포함 헤더 `HideAsanFromProtobuf.h`로 감지 매크로만 지웁니다. 계측은 유지됩니다.
- **잃는 것:** `_DEBUG` 런타임의 반복자 검사, `_DISABLE_STL_ANNOTATION`으로 꺼진 컨테이너 경계 검사. 힙, 스택 오버플로와 해제 후 사용 검사는 남습니다.
- **대안:** ASan 없는 Debug. 구성은 단순하지만 메모리 오류를 잡지 못합니다.

## 요청 제한: 고정 1초 구간

- **결정:** 세션마다 구간 시작 시각과 개수만 저장합니다.
- **이유:** 코드가 짧고 연결당 비용이 작습니다. 구간 경계에서 순간적으로 최대 40개가 통과할 수 있지만 프로토타입에는 충분합니다.
- **대안:** 토큰 버킷. 경계 문제는 없지만 상태 계산이 늘어납니다.

## 프레임 크기 제한: 수신에만 8192

- **결정:** 클라이언트가 보내는 프레임만 8192로 제한합니다. 서버 송신은 길이 필드 한도인 65535까지입니다.
- **이유:** 입력 메시지는 작아서 제한이 서버를 보호합니다. 스냅샷은 개체 수에 비례해 커지므로 같은 제한을 걸 수 없습니다.
- **참고:** 현재 스키마의 스냅샷은 개체당 약 20바이트입니다. 기획서의 11바이트 가정보다 크므로 P5 전송량 판단 때 함께 봅니다.
